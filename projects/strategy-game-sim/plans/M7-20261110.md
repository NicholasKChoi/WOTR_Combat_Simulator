## Design questions

| # | outline(s) | question | why the design does not settle it |
|---|------------|----------|-----------------------------------|
| DQ1 | E | Which auto-house rule replaces "off until the last explicit `build house` step starts"? A) Drop the gate: with `autoHouses` on, auto-houses plan from the start and explicit house steps add houses on top; `auto-houses-never-start` and `auto-houses-held` become unreachable and are removed (OpenAPI change). B) Auto-houses yield only while an explicit `build house` step has been reached (armed) and not started; otherwise they run. `never-start` goes; `held` narrows to that window. C) Keep the gate but open it whenever supply blocks production (reactive: each block costs about one house build time). D) A per-build setting choosing gated or ungated (new input field in schema, paste format, table and OpenAPI). **Recommend A**: simplest rule, matches the "no house steps" result the owner cited (20 villagers, 10 longbows by 7:30), `autoHouses: false` already gives full manual control, and the planner already counts houses under construction so surplus houses arise only when an explicit step lands after the planner acted. | `design/M7.md` covers M7.1–M7.7 only; M7.8 was added after approval (Q22) and the backlog item lists three options without choosing. The choice also decides whether two public warning codes are removed. |
| DQ2 | B | How does the split layout handle a step table wider than its column (backlog: whole ~9100 px Build panel scrolls sideways, row controls hidden at 1280, textarea right border and focus ring clipped)? A) Make the table fit the column: let the fields cell wrap and the run cell stack its times, remove the panel-level `overflow-x`, and keep a table-own scroll box (`step-table-scroll`) as a fallback. B) Only move `overflow-x: auto` from the panel to a wrapper around `<table>`. C) Use the under-768 card layout inside the split column. **Recommend A**: B keeps the scrollbar at the bottom of a long table and the controls hidden; C changes the table look at desktop widths. Test: at 1280 the step table's `scrollWidth <= clientWidth` and the textarea's right edge is inside the column (one `page.evaluate`). | The design adds a column to the table but says nothing about the split-layout overflow; the doc sentence "a Build panel wider than its column scrolls sideways inside the column" would change. |
| DQ3 | D | Does the Text tab show `StepKindLegend` above the editor while annotations exist? **Recommend yes**, same rule as the table (one view shows at a time, so `step-kind-legend` stays unique). | The Legend rule says "above the step table" only; without it the gutter colours are unexplained in the default view. |
| DQ4 | D | Do gutter `li`s hold the times in `step-started`/`step-finished` elements (scoped inside `build-order-line-annotation`)? **Recommend yes**, so the compact-view spec reads times the same way as the table spec. | The DOM contract lists those test ids for `step-run` only; M7.6 says the gutter shows "step-started–step-finished text". |
| DQ5 | D | While the textarea has focus with the caret on step line X, the pointer enters then leaves gutter line Y: does shading go to `null` (last event wins) or back to X? **Recommend last event wins (`null`)**, matching the table rule "leaving with focus still inside clears it". | The gutter rule says pointer enter/leave "acts like a row" and the caret sets the step on `select`/`keyup`/`click`, but not how the two interact. |
| DQ6 | C | After the timeline goes, does the `results-split` wrapper and test id stay? **Recommend remove** both; the specs that read it are rewritten in C anyway. | The design deletes the `.resultsSplit` CSS and rewrites the spec, but does not name the wrapper's fate. |
| DQ7 | B | `results-last-good` sets `aria-describedby="auto-run-status"` while dimmed; during the debounce and `updating` the charts now dim but the status reads nothing (debounce) or `Updating the results.`. Keep `aria-describedby` only for the invalid/rejected/failed statuses, or for every stale state? **Recommend every stale state** except when the status text is empty (debounce), i.e. tie it to a non-empty status message. | Q21 approved dimming during the debounce; the design does not revisit the accessibility hook tied to the old status-only rule. |
