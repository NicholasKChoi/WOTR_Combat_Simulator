## Design questions

| # | outline(s) | question | why the design does not settle it |
|---|------------|----------|-----------------------------------|
| 1 | E, G, H, D | How does Vitest test stateful components and hooks? The design asks for a save status after a 201 or 200 that clears after a settled change, for "two `toggle` calls in one act both apply", and for "the handle's ArrowUp/ArrowDown calls `onMoveKey`". It also names `save-build.test.tsx` and `chart-header.test.tsx`. Either extract pure helpers (for example `saveStatusText(saved, settled)` or a `handleKeyAction(key)` map) and test those with `renderToStaticMarkup`, or add a DOM test environment. | The repo has no jsdom, happy-dom or @testing-library. All component tests are `.test.ts` files that use `renderToStaticMarkup` and cannot fire events, call `act`, or run effects. `vitest.config.mts` includes only `**/*.test.ts`, so a `.test.tsx` file would silently not run. Adding a DOM environment is a new dev dependency and a config change that more than one outline needs, so it should have one owner (A would be the natural place). |
| 2 | C | How is `blob-build-store.live.test.ts` kept out of `npm test`, and what does it do with no credentials? | Its name matches the `lib/**/*.test.ts` include. The design names the script `test:blob-live` but not the exclusion, and not whether a run without a token skips or fails. |
| 3 | C | `landed(key, json)`: how is "our JSON" compared, and what if the landed check itself fails? The options are byte-equal text or a parsed deep-equal, and on a failed check either rethrow or return conflict. | The design defines when `landed` is called, not how it compares or what happens on its own error. A false `conflict` and a false `replaced` have different costs. |
| 4 | E | Where does Escape-to-hide-link attach now that C1 removes the link-panel container that held the `onKeyDown`? If it moves to `save-row`, Escape on `save-build` or `save-build-copy` also hides the link. `copy-saved-link-hint` now sits below the row, outside any Escape scope. | C1 fixes the DOM tree, and the M8 Escape focus target is being restated in the M8.md text fix, but neither names the element that owns the handler in the new tree. |
| 5 | H | After a keyboard move, React reorders the keyed chart sections, which can blur the focused handle. Should the hook refocus the handle by chart id after commit, as the removed `pendingFocus` effect did for the move buttons? Also, `chart-reorder-help` and `chart-order-status` are ids, which assumes exactly one `Results` on the page. | The design states the outcome ("the handle keeps focus") but not the mechanism, and `pendingFocus` is removed with the move buttons. |
| 6 | H, J | The existing `headerControls` prop renders inside the chart body, not the header. C7 needs the view toggle in the header so it works while the chart is collapsed. Confirm that H moves the slot into `ChartHeader`, so J does not have to edit `chart-header.tsx` as well. | C3 and C7 each describe their own part. Neither says which ticket moves the existing slot. |
| 7 | L | When a non-age-up kind is active, age-up markers must still draw, unlabelled. Today unlabelled lines are drawn only for `kind !== 'age-up'`, and age-ups only through the label path. Should the rule become "every marker not in `labelledMarkers` draws as a plain line"? Also, should a pinned run's non-age-up markers stay undrawn, as they are today, so that C6's "pinned marker" means pinned age-ups only? | C8 specifies the labelled set. It does not specify the unlabelled set or pinned markers of other kinds. |
| 8 | I | The `BuildingSeries.name` source. `productionBuildingIds` groups by `baseId` but each civ variant has its own name; does the series use the first variant's name? Does the starting town center count under the same `baseId` as a built one, given capital or landmark variants? | C9 gives `{baseId, name, counts}` and the fixture expectations (`town-center`, `barracks`), not the rule for picking a name across variants. |
| 9 | I | The OpenAPI 2.6.0 change makes `productionBuildings` required on the simulate response. Is that additive enough for a minor bump, given that saved or pinned results are re-simulated and never read back from storage? | The design states the bump, not the compatibility argument. `pin-storage.ts` stores text and re-simulates, so pins are safe; the check is for external API clients. |

Test (b), "height ≤ 0.4 × 720", fails only if the cap is removed. ## Spec gaps

- **M9.10, design/M8.md text fix:** the criterion lists the fix as M9.10 work, but the design (M9.10 row)
  makes it a factory-state edit by the manager or designer, not a ticket. There is no outline for it.
  The manager must apply it, or M9.10 cannot close.
- **M9.10, missing-key rule:** C ships the `ifMatch`-on-a-missing-key mapping "conditional on" the owner's
  live run (owner decision 5A). If the run shows a different SDK behavior than the design assumes, the
  mapping in C changes after review. The ticket should allow a follow-up commit on the same PR rather than a
  new ticket.
- **M9.9 / M9.3 to M9.7, Vitest test shape:** see design question 1. As written, several Vitest cases in the
  Criteria map cannot run in the current test setup (no DOM environment; `.tsx` test files are outside the
  include glob). The owner or designer must choose pure-helper extraction or a DOM test environment before
  E, G and H are written in full.
- **M9.1 TASK-GRAPH row:** SGS-127's criterion column is blank; it should read M9.1.
