## Patterns

### 1. Tests that cannot fail (4 code occurrences, 3 tickets reworked, 1 merged)
Evidence:
- SGS-007 rework 1 (review, `reports/SGS-007-review.md`): `utils/utils.test.ts:5,13` used already-sorted
  inputs, so an in-place sort passed every test.
- SGS-005 rework 1 (review, `reports/SGS-005-review.md`): `simulate.test.ts:91` "integer arithmetic for N = 30"
  also passes with the float form it claims to rule out.
- SGS-014 rework 1 (review, `reports/SGS-014-review.md`): the ascending-age `byBaseId` test cannot fail,
  because upstream entries are already in age order; deleting the sort still passes.
- SGS-010 (bug ticket): the malformed-JSON acceptance test written under SGS-003 passed through the handler's
  shape 400, not the body parser's `Invalid JSON` 400. It passed review and acceptance on SGS-003 and SGS-006
  and was only noticed by the SGS-006 implementer.
- Same class at spec time: SGS-010 spec-gate 1 (mutation criterion unfalsifiable), SGS-015 spec-gate 1
  (palette criterion untestable under SSR).

Root cause / escape point: test gap. Escape point is the implementer (unit) and acceptance-test (harness).
`common.md` "Tests" already says "ask what change would make this fail", but nothing makes the author run that
change, and the inputs (sorted, in-order) made the wrong implementation indistinguishable. The ticket agent got
a mutation self-check in engine commit 5f54fb0, but that only covers criteria that name a mutation.

Proposal (engine): `agents/implementer.md`, section "Unit tests", append:

```
For each test that encodes a behavior, name the one-line production change that should break it, apply it,
confirm the test fails, and revert. Pick inputs where a wrong implementation gives a different answer:
unsorted input for sort or no-mutation tests, reverse order for ordering tests, a top-level write for freeze
tests. List each test with its mutation in the report.
```

Same paragraph in `agents/acceptance-test.md` for harness specs (for HTTP status checks: name the other code
path that returns the same status, and assert something only the intended path produces).

### 2. Lockfile `name` set to the worktree folder (3 occurrences; recurred after an engine fix)
Evidence: SGS-007 rework 1 (`package-lock.json:2` became `"sgs-007-unit-test-runner"`); SGS-002 manager note
2026-10-28 (manual recheck needed after rebase); SGS-015 rework 1 (`"sgs-015-aoe4-series-chart"`), run log
14:49 "third occurrence". The engine rule in `agents/implementer.md` ("Revert ... a package `name` set to the
worktree folder", commit 586857e, 2026-10-29) predates SGS-015 and did not stop it (sonnet implementer).

Root cause / escape point: tooling gap in the repo. `package.json` has no `name`, so every `npm install` in a
worktree rewrites line 2 of the lockfile. Escape point: implementer; review caught every one, at the cost of a
full rework cycle each.

Proposal (repo): remove the cause instead of policing it. A small `site` ticket: add
`"name": "wotr_combat_simulator"` and `"private": true` to the root `package.json` and regenerate the lockfile
once (the lock's name changes from `WOTR_Combat_Simulator` to the lowercase package name; npm rejects
uppercase names in `package.json`, so the current lock value cannot be kept verbatim). Until it merges, add to
`$FACTORY_DIR/LESSONS.md`:

```
- After any npm install in a worktree, `git diff package-lock.json | grep '"name": "sgs-'` must print nothing; restore line 2 if it does.
  Why: package.json has no name, so npm writes the worktree folder into the lockfile (SGS-007, SGS-002, SGS-015 reworks).
```

### 3. Tickets fence out the docs their change makes false (3 follow-up tickets or re-specs)
Evidence:
- SGS-009: a whole ticket to fix `docs/combat-simulator.md` input-bounds text, because SGS-003 "forbade edits
  under `docs/`" (SGS-009 Source line; `reports/SGS-003-review.md` finding 1).
- SGS-023: a whole ticket for `ARCHITECTURE.md` Stack versions, because SGS-012's scope did not touch docs.
- SGS-004 re-spec 2 and spec-gate 3: stale "Current code" notes in `docs/combat-simulator.md` needed an owner
  ruling to be edited in-ticket; run log 18:36 `needs-you: follow-up ticket for stale 'Current code' paragraph`.
- `ARCHITECTURE.md:40` already says "A change to an app's rules updates `docs/<app>.md` in the same PR".

Root cause / escape point: spec gap. Escape point is the ticket agent; spec-gate's checklist has no item for
it, so all three passed spec-gate.

Proposal (engine): make spec-gate check one more thing. `agents/spec-gate.md`, add after item 10:

```
12. **Docs it makes false.** Every repo doc that states a rule, version, path, or behavior this ticket
    changes (the app design doc, ARCHITECTURE.md, README, API schema) is edited in Scope, not listed
    under Out of scope. A doc left stale is a gap; name the doc and the line.
```

and in `agents/ticket.md` "Write", one bullet: "Grep the repo docs for what Scope changes; edit the ones it
makes false in this ticket."

### 4. Milestone design incomplete when tickets are cut (4 re-specs and 1 rework in M2)
Evidence:
- SGS-013 rework 1 (`reports/SGS-013-review.md` findings 3 and "Spec gaps"): design/M2.md named issue codes
  but not which code covers a JSON shape error or a villager `produce` without `rally`; `times` endpoints

  doc copied (run log 14:52).

  dropped); designer relaunched 14:25.
- SGS-014 re-spec 1: starting state, supply values and walk defaults had no source; designer ratified 4
  questions (run log 13:38-13:40).
- The M2 designer ran 9 times (11:55 to 14:50), 5 of them after tickets were written.

Root cause / escape point: spec gap in the design. Escape point is the designer. Owner decisions (Recharts,
walkSeconds) are legitimate churn and excluded; the cases above are omissions any contract review would find.

Proposal (engine): `agents/designer.md`, section "Write", add a bullet before "Stay under ~150 lines":

```
- Before reporting, check the Contracts for completeness: the initial state of every simulated or stored
  entity; for every error or issue code, the inputs that produce it, with every rejected input mapped to
  exactly one code; for every sampled or series output, its first and last sample; every enum value a table
  uses exists in its type. List anything you leave open under Left to tickets.
```
