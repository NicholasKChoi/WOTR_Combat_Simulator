## Context

Today the only way to edit a build on `/apps/aoe4-build-order` is the paste textarea (`build-input.tsx`), and a typo is only reported after Run. M3.4 asks for a table of steps with dropdowns for the valid ids, kept in sync with the text: the page holds one `text` state, the table renders `parseBuildOrderText(text)`, and a table edit writes back `formatBuildOrderText(newOrder)`. SGS-040 makes that safe by giving the formatter every step form the grammar can read.

## Scope

Names follow `design/M3.md` and the written tickets SGS-035, 037, 038, 039, 040 and 045. File paths and line numbers refer to `main` f078c11 and shift once the earlier M3 tickets land; SGS-045, 047, 048 and 049 also edit the page and `results.tsx`, so rebase and never rewrite their lines.

**`lib/aoe4-build-order/step-options.ts`** (new, pure; imports `GameData` and `classifyTech` from `effects.ts`; no React). Exports `StepOptions` (exactly the design's shape: `actions`, `triggerKinds`, `nodes`, `finiteNodes`, `resources`, `buildings`, `producers`, `villagerProducers`, `unitsByProducer`, `techs`, `techSites`) and `stepOptions(data: GameData): StepOptions`.
- `actions` is `produce, pause, build, research, move, rally` (this order, as the design comment lists them). `triggerKinds` is `none, time, villagers, depleted, bank`. `nodes` is `NODE_REFS`, `finiteNodes` is `FINITE_NODE_REFS`, `resources` is `RESOURCE_KINDS` (read from `model.ts`, never re-listed).
- `buildings` is every `type: 'building'` baseId in `data.byBaseId`. `producers` is the building baseIds that appear in any unit's `producedBy`. `villagerProducers` is `producedBy` of the entries whose baseId is `VILLAGER_ID` (`engine-common.ts`). `unitsByProducer[p]` is the unit baseIds whose entries list `p` in `producedBy`. `techs` is the baseIds of `technology` and `upgrade` entries for which `classifyTech(entry, data).kind !== 'rejected'` for every entry of that baseId (the validator rejects a tech when any entry is rejected: `validate.ts` `checkField`). `techSites[t]` is the union of `producedBy` over that tech's entries.
- Ordering (design): every id list is sorted by the lowest `age` among the id's entries, then by `baseId` ascending (plain code-unit comparison, not locale). The three constant lists keep their constant order. The result is plain arrays and records, safe to serialize as static props (no `Map`, `Set` or `undefined` values).
- Lookups go through the `Map`s on `GameData` (the `__proto__` rule in `data.ts`); `unitsByProducer` and `techSites` are built with `Object.fromEntries` from those lookups.

**`components/apps/aoe4-build-order/step-table-model.ts`** (new, pure, no React). Imports `BuildStep`, `Trigger`, `NodeRef` etc. from `lib/aoe4-build-order/model` and `StepOptions` (type) from `step-options`; value imports only `VILLAGER_ID` and `HOUSE_ID` from `engine-common.ts`. It must not import `data.ts`, `validate.ts` or `simulate.ts` as values (the browser bundle never contains the game data). Exports the design's names:
- `defaultStep(action, options): BuildStep`: `produce` is `{ action: 'produce', producer: villagerProducers[0], unit: VILLAGER_ID }`; `pause` is `{ producer: villagerProducers[0] }`; `rally` is `{ producer: villagerProducers[0], to: nodes[0] }`; `build` is `{ building: HOUSE_ID, from: 'wood' }`; `research` is `{ tech: techs[0] }` (no `at`); `move` is `{ count: 1, from: nodes[0], to: 'wood' }`. No trigger, no optional field. (Values fixed by the design's `defaultStep values` row; each validates against the English data.) (respec 1)
- `defaultTrigger(kind, options): Trigger` for kinds other than `none` (values fixed by the design) (respec 1): `time` 0, `villagers` 1, `depleted` `finiteNodes[0]`, `bank` `{ resource: resources[0], atLeast: 100 }`. All within `SIM_INPUT_BOUNDS`.
- `insertStep(steps, index, step)`, `deleteStep(steps, index)`, `moveStep(steps, index, delta)` (delta is -1 or 1; a move off either end returns `steps` unchanged), `replaceStep(steps, index, step)`: each returns a new array, never mutates, and returns the same array when `index` is out of range.
- `changeAction(step, action, options)`: `defaultStep(action, options)` carrying over `trigger` and `reaction` of `step`; the same action returns `step` itself (design: no-op).
- `selectChoices(value, choices): { id: string; unknown: boolean }[]`: every choice in order with `unknown: false`; when `value` is not among them, one more entry `{ id: value, unknown: true }` at the end. An undefined value adds nothing.
- Helpers the table needs, named by the implementer and exported from this file only: change producer (if `unit` is not in `unitsByProducer[producer]`, `unit` becomes that list's first entry), change trigger kind (`none` removes `trigger`; another kind sets `defaultTrigger`; leaving `depleted` removes `reaction`; the same kind is a no-op), set reaction (`true` sets `reaction: true`, `false` deletes the key), and set a number field. The number rule (design): the text must match `^\d+$` (an unsigned integer, no sign, no decimals, no exponent) or, for `move.count` only, be exactly `all`. An empty optional field (`count`, `builders`, `instance`, `walkSeconds`) deletes the field. An empty or non-integer required field (`move.count`, trigger `seconds`, `count`, `atLeast`) returns the step unchanged. Bounds are not checked here.

**`components/apps/aoe4-build-order/step-table.tsx`** (new). `StepTable({ order, options, onChange })` where `order` is the parsed `BuildOrder` and `onChange(next: BuildOrder)` is called with `{ ...order, steps }` for every edit. One `step-row` per step (`data-step` is the 0-based index). Columns: trigger kind select (`step-trigger-kind`) and its fields (`time`: `step-field-seconds`; `villagers`: `step-field-trigger-count`), action select (`step-action`), the action's fields, the reaction checkbox, and the buttons `step-move-up`, `step-move-down`, `step-delete`; below the rows, `step-add`.
- Fields by action follow `STEP_FIELDS` in `validate.ts:62-69`, every one rendered whether or not it is set, so a pasted value is always visible: `produce` producer, `instance`, unit, `count`, `rally`, `walkSeconds`; `rally` producer, `instance`, `to`, `walkSeconds`; `pause` producer, `instance`; `build` building, `builders`, `from`, `then`, `walkSeconds`; `research` tech, `at`; `move` `count`, `from`, `to`, `walkSeconds`. Trigger fields: `time` `seconds`, `villagers` `count`, `depleted` `node`, `bank` `resource` and `atLeast`. Each control has `data-testid="step-field-<field>"` where `<field>` is the JSON name. A `villagers` trigger's count is `step-field-trigger-count`, because a row can also hold `produce ... x3` or `move 4 ...`, whose `count` is `step-field-count`. (The design's test-id table names `step-field-trigger-count`; SGS-055 uses it.) (respec 1)
- Selects take their choices from `options`: producer from `producers` (`rally` action: `villagerProducers`), `unit` from `unitsByProducer[producer] ?? []`, `building` from `buildings`, `tech` from `techs`, `at` from `techSites[tech] ?? []` plus an empty option meaning none, node fields from `nodes` (`then` and `rally` carry an empty option), trigger `node` from `finiteNodes`, `resource` from `resources`. Each goes through `selectChoices`, so a value the options do not list renders as an extra selected `<option>` labelled `<id> (unknown)` with `data-unknown="true"`, and the table never rewrites it by itself (a change of another field leaves it alone, except the producer-to-unit rule).
- Number fields (`step-field-count`, `-builders`, `-instance`, `-walkSeconds`, `-seconds`, `-atLeast`) are text inputs with `inputMode="numeric"`. Each keeps a local draft string while focused so a user can clear a field to retype it; the step changes only when the draft passes the number rule (an invalid draft leaves the step as it was), and on blur the field shows the step's own value again. Per the design, the time field (`step-field-seconds`) takes whole seconds (matching `Trigger.seconds`), not `m:ss`, and its label says "seconds". (respec 1)
- `step-field-reaction` is a checkbox rendered only while the trigger kind is `depleted`.
- Move up is disabled on row 0 and move down on the last row (`disabled` attribute). Delete removes the row; deleting the last row leaves `steps: []`.
- `start` is shown read-only above the rows as the printed `start` line (read from the parsed order; `formatBuildOrderText` of an order with no steps and that `start`). With no `start`, the row is omitted.
- Keys: rows are keyed by index (the table has no per-row state besides drafts, which are dropped on blur).

**`components/apps/aoe4-build-order/build-input.tsx` and `pages/apps/aoe4-build-order.tsx`**
- `PageProps` gains `options: StepOptions`; `getStaticProps` returns `{ builds, options: stepOptions(loadGameData('english')) }`. The browser bundle must not import `data.ts` (`getStaticProps` imports are server-only, as `listBuilds` is today).
- The page keeps the one `text` state it has. It computes `parsed = useMemo(() => parseBuildOrderText(text), [text])` and renders, between the build input form and the results, a section with `StepTable` when `parsed.ok`, else `step-table-unavailable` holding the first issue's `message`. `onChange(order)` calls `setText(formatBuildOrderText(order))`. Typing in the textarea never rewrites `text` (no format on change); choosing a prebuilt build still sets `text`, and the table follows. `BuildInput` is not changed beyond keeping its props (the table is a sibling, not part of the form: a button inside the table must not submit the form, so every table button is `type="button"`).
- Run posts the current `text` (unchanged M2 code). Editing during a run is allowed; the result shown stays the one requested.
