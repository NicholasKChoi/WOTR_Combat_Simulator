## Context

Every upgrade dot on the Units chart (`chart-upgrade-dot`, and the pinned `chart-pinned-upgrade-dot` ring) looks the same: a dot in its line's colour. Which upgrade it is shows only in the SVG `<title>` hover text, so a reader cannot tell the tiers apart at a glance. This adds a visible tier name beside each dot. The type stays Chore by owner decision (PROJECT.md Decisions: "A backlog item the owner tags `(standalone chore)` stays a Chore even when it adds small visible UI text (owner 2026-11-18, Q138); the spec-gate and review do not bounce it for changing visible behavior."), so the visible tier text is not a Chore contract finding; no simulation or chart data changes, and the existing dot properties (colour, outline, position, title, visibility rules) stay. The acceptance gate still runs on this ticket, because the diff adds acceptance specs.

The tier is already in the data. A dot's `label` is the research `baseId` and its `key` is the unit it upgrades: `researchMarker` in `lib/aoe4-build-order/markers.ts` sets `label` to the `baseId` and `unit` to the `upgradeTargets` value (called from `researchItem` in `lib/aoe4-build-order/research.ts`), and `unitUpgradeDots` in `components/apps/aoe4-build-order/result-series.ts` copies `unit` into `key`. The English `upgradeTargets` (`data/aoe4-build-order/rules/english.json`) maps ids such as `veteran-longbowmen` to `longbowman`, `elite-knights-or-lancers` to `knight`, and three ids to `man-at-arms`: `early-men-at-arms`, `men-at-arms` (the upgrade to the standard tier, whose id is the unit's plural with no tier word) and `elite-men-at-arms`. Because ids use the plural (`longbowmen`, `men-at-arms`) and the key the singular (`longbowman`, `man-at-arms`), the rest of an id never equals its key letter for letter; the rule below compares hyphen segment counts instead. No shipped build researches two tiers of one line (each researches `veteran-*` only). The `elite-*` upgrades need age 4, which no run reaches (the start age is data and the landmark rule covers ages 1 to 3), so a run cannot show two tiers through an elite upgrade; it can through the men-at-arms line: researching `early-men-at-arms` and then `men-at-arms` puts two dots on the Man-at-arms line a few seconds and about one unit apart, and their texts, each placed beside its own dot, overlap (review 6 measured "Early" and "Upgrade" drawn over each other at 1280 px). Two upgrades at exactly one instant happen only with a start age set in data (a scratch unit run at `origin/main`), and with a pinned run whose upgrade lands where the current run's does.

## Scope

- **Tier name.** A pure exported function in `components/apps/aoe4-build-order/result-series.ts` (next to `unitUpgradeDots` / `visibleUpgradeDots`; the branch names it `upgradeTierName`) that takes an upgrade dot's `label` (the upgrade id) and `key` (the unit id) and returns the text drawn beside the dot. The rule, exactly:
  - Split the id and the key on `-`. When the id has more segments than the key, the tier is the id's first segment with its first letter upper-cased and the rest unchanged (`veteran-spearmen` with `spearman` gives `Veteran`; `early-men-at-arms` with `man-at-arms` gives `Early`; `elite-knights-or-lancers` with `knight` gives `Elite`).
  - Otherwise (the id has no more segments than the key, as `men-at-arms` with `man-at-arms`) the id has no tier word and the function returns the fallback text `Upgrade`.
  - No list of tier words or unit names appears in the code; the function works from the two ids alone.
- **Placement.** Pure exported functions in the same file decide where each tier text sits relative to its dot, given the dots one chart draws (current and pinned) and the plot's bounds, in whatever shape the implementer needs (the branch splits this into `tierTextSlots`, which groups texts, and `placeTierText`, which places one text from its dot's box and its group slot). The decision is made in pixel space: from each dot's position on the plot and each text's box size (estimated, as the branch does with `estimateLabelWidth` from `chart-markers.ts`, or measured, as `SeriesChart` does for marker labels with `measureRef`), never by comparing the dots' times and values. The branch's `tierTextSlots` groups dots only by equal time and value (`at:value`), which is the defect review 6 found: two dots a few pixels apart get separate groups and texts drawn over each other. The rules:
  - A text sits beside its dot and does not cover its dot's point.
  - Any two tier texts on one chart (current or pinned) whose boxes would intersect where each would sit alone get positions where their boxes do not intersect. Dots at one point (two current dots of different upgrades at one instant, or a pinned ring and a current dot) are one case of this, not the only one.
  - A text that would cross the plot's right edge is moved to the other side of its dot, and texts stay inside the plot's top and bottom edges (as `placeMarkers` in `chart-markers.ts` flips marker labels).
  - Where the pixel positions come from (the plot box and axis domains `SeriesChart` already has, recharts' own scale or plot hooks, or the dots' rendered boxes) is the implementer's choice; the rules hold whatever the chart's width or zoom window.
- **Render.** In `SeriesChart` (`components/apps/aoe4-build-order/line-chart.tsx`), draw the tier name through each `ReferenceDot`'s `label` prop with a content element or render function (the `currentDots` and `pinnedDots` blocks), placed by the placement functions, so the text is the app's own `<text>` and carries no `recharts-label` class. Each current dot's text has `data-testid="chart-upgrade-tier"` and each ring's text `data-testid="chart-pinned-upgrade-tier"`, each with the same `data-series`, `data-label` and `data-at` as its dot. Text size and the legibility treatment (outline or halo against the plot) are the implementer's to choose from the chart's existing label styling (`LABEL_FONT_SIZE`). Both texts are in their line's colour; the current dot's text is fully opaque and the ring's text is drawn at a lower opacity, matching the pinned run's fainter styling. The dot itself keeps its `data-testid`, `data-series`, `data-label`, `data-at`, fill, stroke, dash, radius, layer order and `<title>` text.
- The tier text follows its dot: it is drawn exactly when its dot or ring is (hidden with the line in the series legend, absent outside a zoom window, absent in the Buildings view and the other charts).
- **Docs made untrue:** `docs/aoe4-build-order-ui.md`, the "Upgrade dots" paragraph, describes the dot's and ring's label and time only as a hover title and says nothing of visible text; it must state that each dot and ring shows its tier name as visible text, the tier rule with its fallback, and the placement rule. On the branch the paragraph says "texts of dots and rings at one point stack at different heights", which covers only dots at one point; it must state the overlap rule above instead. `components/apps/aoe4-build-order/page-help.tsx`, the Units chart paragraph on upgrade dots, says only when an upgrade lands; it must say the dot names its tier. The implementer writes the wording against the code it builds; the help paragraph keeps the phrases `upgrade dot` and `unit line` that `aoe4-help-modal.spec.ts` checks.
- **Tests.** Unit tests for the tier-name and placement functions beside the `result-series.test.ts` cases; acceptance cases in `acceptance/aoe4-units-chart-upgrade-dots.spec.ts`. Every acceptance comparison of layout values (dot and ring positions, text rects, the plot box) reads all the values it compares in one `evaluate` inside `expect.poll` or `toPass` (LESSONS.md; `readLayout` in `acceptance/helpers.ts` is one such helper, or a spec helper that reads every selector the comparison needs in one call). The branch's pin test reads the rings and the dots in two `readTiers` calls, which this rule forbids. Existing tests keep their assertions (this is a Chore). The search for specs that read chart SVG text found selectors on `text.recharts-label` (examples: `aoe4-chart-readability.spec.ts`, `aoe4-marker-labels.spec.ts`, `aoe4-chart-zoom.spec.ts`, `aoe4-build-order-pin-compare.spec.ts`, `aoe4-chart-layout.spec.ts`) and text counts under marker line layers; the new text has no `recharts-label` class and sits in the dot's layer, so none of them sees it. The dot selectors (`chart-upgrade-dot`, `chart-pinned-upgrade-dot`) match the circles, not the text. Should an existing test still need an edit, the implementer lists each one and why.

**Out of scope:** changing which dots are drawn or where (`visibleUpgradeDots`); the marker control and vertical marker lines; the series legend; the simulation, data files, marker labels or `markers.ts`; the Buildings view; any change to dot size or colour.

## Acceptance criteria

- [ ] (respec 3) Tier-name unit test, looped over every entry of the English data's `upgradeTargets` (id and target unit, read from the loaded data, not a hand-typed list): when the id has more `-` segments than its target, the result is one word with no hyphen, starts with an upper-case letter, equals the id's first segment ignoring case, and is shorter than the id; otherwise the result is `Upgrade`. Named cases with target `man-at-arms`: `early-men-at-arms` gives `Early`, `men-at-arms` gives `Upgrade`, `elite-men-at-arms` gives `Elite`. An invented id and key not in the data, `mighty-widgets` with `widget`, gives `Mighty`. A test fails if the function returns the whole id, returns `Men` for `men-at-arms`, returns the same text for a `veteran-*` and an `elite-*` id, or works from a list of known tier words or units.
- [ ] (respec 2) Placement unit tests cover: two dots at different times and values whose pixel positions are a few pixels apart, so their texts would intersect if each were placed alone, get text boxes that do not intersect; dots at one point (current or pinned) get text boxes that do not intersect; a dot near the plot's right edge, and one near its top edge, get a text box inside the plot bounds; a text box never covers its own dot's point. A test fails if the placement groups dots only by equal time and value, or ignores an edge.
- [ ] (respec 1) On the Knight/Longbow build in the Units view, each current upgrade dot has a `chart-upgrade-tier` text with the dot's `data-series`, `data-label` and `data-at`, whose content equals what the tier-name function returns for that dot's label and series, with a non-empty Chromium bounding box inside the chart's plot. The spec reads the text and dot positions in one `evaluate` inside `expect.poll` or `toPass`.
- [ ] (respec 2) Different tiers show different, readable text: a run whose build text is edited to research `early-men-at-arms` and then `men-at-arms` (a second tier on the Man-at-arms line, which the run produces) shows two dots on that line whose tier texts differ, each equal to the tier-name function's result for its dot, and whose text rects do not overlap. The spec asserts non-overlap with an intersection check on both rects (the spec's `overlap(a, b)` is false), not a check that the boxes are not identical, and reads both rects in one `evaluate` inside `expect.poll` or `toPass`; the check fails on the branch's exact-point grouping.
- [ ] (respec 2) With a pinned run, each `chart-pinned-upgrade-dot` has a `chart-pinned-upgrade-tier` text beside it; its computed opacity (element `opacity` times `fill-opacity`) is lower than a current tier text's, which is 1. With the same build pinned and shown again, the ring's text and the dot's text at one point have rects that do not overlap. The ring and dot positions and both texts' rects that this compares are read in one `evaluate` inside `expect.poll` or `toPass`, never from separate calls.
- [ ] The text follows its dot: hiding the line in the series legend removes its tier texts (current and pinned); a zoom window that excludes the upgrade removes them; the Buildings view and the other charts have none; showing the line or the Units view again brings them back. A test fails if a text stays while its dot is gone.
- [ ] (respec 1) A dot near the plot's right edge (for example under a zoom window that ends just after the upgrade) has its tier text's bounding box fully inside the plot.
- [ ] (respec 1) The dots' existing properties are unchanged: the assertions in `aoe4-units-chart-upgrade-dots.spec.ts` and `aoe4-help-modal.spec.ts` on `data-testid`, `data-series`, `data-label`, `data-at`, fill, stroke, dash, radius, layer order and `<title>` text stay as they are, and no tier text carries the `recharts-label` class; `typecheck` and the unit suite pass.
- [ ] (respec 2) `docs/aoe4-build-order-ui.md`'s "Upgrade dots" paragraph states that each dot and ring shows its tier name as visible text, with the rule (the upgrade id's leading word when the id is longer than the unit's id, else `Upgrade`), and the placement rule: texts that would overlap, not only texts of dots at one point, are moved apart; no sentence limits the separation to dots at one point. The help text in `page-help.tsx` says the dot names its tier and does not contradict the doc.
- [ ] No INVARIANTS.md regressions: no tier word or unit name is hard-coded in the tier-name function (A1).
