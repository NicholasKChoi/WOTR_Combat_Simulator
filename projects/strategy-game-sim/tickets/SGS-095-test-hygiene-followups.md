## Scope

Test and test-helper files only. Paths relative to the repo root.

1. **Hard-coded step index (respec 3: conditional on SGS-098).** Applies only if, after SGS-098, `acceptance/aoe4-simulate-api-spear-longbow-build.spec.ts` still has a test that uses `MAN_AT_ARMS_STEP`. If SGS-098 deletes every such test (the spec's two men-at-arms timing tests are among the 28 failing on origin/main), item 1 and criteria 1 and 2 drop: discard the branch's edit to that spec (or let it vanish with the deleted tests), and the report says so. Otherwise keep it, covering the remaining uses. `acceptance/aoe4-simulate-api-spear-longbow-build.spec.ts` has `const MAN_AT_ARMS_STEP = 34`, used in `steps.find((s) => s.step === MAN_AT_ARMS_STEP)`. The API result's `steps` carry only the index (`StepTiming.step` in `lib/aoe4-build-order/model.ts`), but the spec already imports the build JSON. Derive the index from `spearLongbow.steps` as the first step with `action === 'produce'` and `unit === 'man-at-arms'` (today that is the step triggered at the Castle landmark second; later men-at-arms steps carry an `instance`). Fail loudly (throw) when no step matches. A `.find` or a `findIndex` plus throw both work; the JSON import types `action` and `unit` as plain strings, so no cast is needed. Keep `CASTLE_LANDMARK_SECONDS` and `MAN_AT_ARMS_START_SECONDS` as they are.
2. **Schema table titles and collection-time work.** In `lib/aoe4-build-order/schema.test.ts`, `describe('quoted ids in issue messages')` builds `cases` with `sites.flatMap(...)` in the describe body, calling each row's `run(value)` and `expected(...)` while collecting, and the `it.each` title ends in `%#` (prints the row index, for example "is quoted as 2"). Change so each `it` computes `run(value)` and the expected tail inside the test body (rows hold site, length, and the value or the inputs to build it), and the title states the rule without the index (for example `'%s: a %i character value is quoted whole up to 40 characters and cut with "..." beyond'`, wording the implementer's choice, no `%#`). A thrown schema error then fails one test instead of the whole file at collection. The `simIssues` and `rally` helper definitions and the `sites` row closures may stay in the describe body; they only reference `checkSimInputs` and `messages` inside function bodies and must not be invoked there.
3. **Stale pin comment.** In `lib/aoe4-build-order/simulate-house-warnings.test.ts`, the `it.each` in `describe('timing with the auto-house warnings')` has a comment above the `ENG Spear/Longbow into MAA/Crossbow` row beginning "Re-pinned for villagerTarget: ...". The task as given quoted "Re-pinned for the house lead-time rule"; main already carries different wording, but the comment is still a change-history note that describes one past re-pin and goes stale at the next one. Delete it (the file's other comment above the digests states the lasting rule). Do not change any pinned digest.
4. **Flaky `waitForResponse` in `acceptance/combat-simulator-battles.spec.ts`.** The test 'clearing battles shows the server error and no results' timed out waiting for the `/api/fight` POST once in a full `npm run acceptance` run and passed 7/7 alone. Suspected cause, to be confirmed by the implementer: the `test.beforeEach` waits only for `networkidle`, which does not mean React has hydrated `pages/apps/combat-simulator.js`; a click on `Fight!` before hydration submits the form natively (no `onSubmit` handler yet, so no `fetch`, and the page reloads), and the response wait never resolves. Full-suite load widens that window. The same `goto` + `networkidle` beforeEach is copied in `acceptance/combat-simulator.spec.ts` and `acceptance/combat-simulator-validation.spec.ts`, and (respec 2) the test 'Fight! with 10/0/5 vs 0/10/5 renders the Army Results table' in `acceptance/fight-api-caps.spec.ts` does the same `goto('/apps/combat-simulator')` + `networkidle` inline before clicking `Fight!`, so it has the same race. Reproduce under load first (for example `npx playwright test combat-simulator --repeat-each=10 --workers=4` or the full suite) and record the exact command and the evidence in the report. (respec 1) Then replace the `networkidle` wait with one helper exported from `acceptance/helpers.ts` (name chosen by the implementer) that the three combat-simulator specs call from their `beforeEach` and (respec 2) that the `fight-api-caps.spec.ts` test above calls in place of its two inline lines: it calls `page.goto('/apps/combat-simulator')` and then `page.waitForFunction` until the `#fight-form` element has an own property whose name starts with `__reactProps$` (React DOM sets it on the element when it hydrates and attaches `onSubmit`; it is absent in the server HTML). The page has no other DOM signal: `#fight-form` renders identically before and after hydration and carries no `data-*` marker. No product code change (no hydration marker in `pages/apps/combat-simulator.js`), no fixed sleep, `waitForTimeout`, or click-retry loop. The helper change is a race fix and is required even when the reproduction does not show the flake; in that case the report says the flake did not reproduce and gives the command and repeat count. If the reproduction shows an additional cause (for example the first `/api/fight` compile in `next dev` exceeding a timeout), fix that too within the out-of-scope limits below and say so in the report.

**Out of scope:** product code, `playwright.config.ts` timeouts or retries (a retry would hide the race), the AoE4 acceptance specs' own waits (including the `networkidle` in `openPage` in `acceptance/helpers.ts`, which stays as it is), any digest or expected-value change.
