- **Component**: aoe4-build-order

- **Risk**: standard

## Context

M7 puts the build order's run result on the build itself. SGS-107 to SGS-109 added the annotation model, the step table's run cell and row hover shading, and the page's active-step state. The default Text view still shows none of it. M7.6 (owner decision: the Text-tab gutter is the compact view) draws one annotation per step line in a second gutter beside the textarea, from the same `BuildAnnotations` the table reads, so both views show the same colours and times.

Changes:

1. `components/apps/aoe4-build-order/step-annotations.ts`: add `annotationsByLine(annotations: BuildAnnotations, stepLines: readonly number[], lineCount: number): (StepAnnotation | null)[]`. The result has length `lineCount`; index `stepLines[i] - 1` holds `annotations.steps[i]`; every other index is `null` (blank, comment, `start` and unparseable lines). A step line number outside `1..lineCount` is ignored.
2. `components/apps/aoe4-build-order/build-text-editor.tsx` (`BuildTextEditor`): new props `annotations: BuildAnnotations | null`, `lines: BuildOrderLines` (the live parse's lines), `activeStep: number | null`, `onActiveStepChange: (runStep: number | null) => void`. Rename the component's local `const lines = lineCount(text)` (a number) to `rowCount` so it does not collide with the `lines` prop.
   - While `annotations !== null`, render a second `ol` (`data-testid="build-order-annotations"`, `aria-hidden="true"`) between the line-number gutter and the textarea, with one `li` per text line, built from `annotationsByLine(annotations, lines.steps, rowCount)`. While `annotations === null` the `ol` is not rendered.
   - A `li` for a step line (`data-testid="build-order-line-annotation"`, `data-line`) shows: the kind as a left border in the kind colour (`KIND_CLASS`, every kind including `other`); when `annotation.run !== null`, `<StepTimes run={annotation.run} />` imported from `step-annotation.tsx`, rendered unconditionally in that case (the `step-started` and `step-finished` elements, same test ids as the run cell, read scoped inside the `li`); and a `title` holding Waited and Blocked by (wording is the implementer's; it carries `formatWaitBreakdown` text). The en dash for a run with no times (`not-reached`, `waiting`) is what `formatStepTime` and `finishedText` (SGS-107) return for that run; `StepTimes` passes their text through and the gutter adds none. When `annotation.run === null` the `li` shows what SGS-108's `StepRunCell` shows for that case: the kind border only, no `StepTimes`, no `step-started` or `step-finished`, no warning background (the gutter shows no badge for any kind; the kind colour is the border). It carries `data-kind`; when `run` is set, `data-status`, `data-flagged="true"`, `data-long-wait="true"`, as the table's row does; `data-stale="true"` while `annotations.stale`. Its class list includes `annotationToneClass(annotation.run ?? undefined, annotations.stale)` (`StepAnnotation.run` is `StepRun | null`; the function takes `StepRun | undefined`; SGS-108's signature does not change), so the warning background and the stale opacity are the same rules as the run cell. This ticket makes no change to `StepRunCell` or any other part of `step-annotation.tsx`.
   - The active gutter line: `data-gutter-active="true"` on the `li` while `run.runStep === activeStep` and `activeStep !== null`. Never `data-active`: SGS-109's check that exactly one element in the page has `data-active="true"` must still hold. The active `li` also gets a visible style (a computed `box-shadow` or background that differs from an inactive `li`).
   - Blank, comment, `start` and unparseable lines get an empty `li` (`data-testid="build-order-line-annotation"`, `data-line`, no `data-kind`, no times).
   - Column CSS goes in `workbench.module.css`, next to the shared `.gutter, .textarea` rule (extend that rule so the font and line height match, so rows align). The annotation `li` box model: one line at `height: 1.5em` (the same line height as the line numbers and the textarea rows), `white-space: nowrap`, `overflow: hidden`, `text-overflow: clip`; the two times sit on one line (`step-started`, then `step-finished`); the column has a fixed width in `ch` or `rem` (the implementer picks one wide enough for two `formatStepTime` strings) with `flex: none`; the textarea keeps `min-width: 0` and takes the rest of the row. At 1280 px the Build panel does not scroll sideways after a run (SGS-108's Text-view layout check, which reads the textarea's right edge against `panel-build` after a run, must still pass). At 390 px the editor row never exceeds the viewport width: the rule is that the annotation column has a fixed width and the textarea has `min-width: 0`, so the editor row fits at any width; no new 390 px test is added.
   - Hover: pointer enter on a `li` whose annotation has a `run` calls `onActiveStepChange(run.runStep)`; pointer enter on a `li` with no `run` or no annotation calls `onActiveStepChange(null)`; pointer leave calls `onActiveStepChange(null)`.
   - Caret: on the textarea's `select`, `keyup` and `click` events, read the caret line from `selectionStart` (the 1-based line number of that offset in the text), and call `onActiveStepChange` with that line's `run.runStep`, or `null` for a non-step line, a line with no `run`, or when `annotations === null`. Textarea `blur` calls `onActiveStepChange(null)`.
   - Last event wins: no state in the editor remembers the caret line. With the caret on step line X, the pointer entering gutter line Y sets Y's step and leaving Y sets `null`; it does not return to X until the next caret event.
   - Legend: render `StepKindLegend` above the textarea row (below the label) while `annotations !== null` and `lines.steps.length > 0`. That holds while the text has a syntax error and its partial parse still has steps (the table's `step-table-unavailable` exception does not apply to the Text view). Only one editor view renders at a time, so the default `step-kind-legend` test id stays unique; this ticket does not pass `testId`.

## Acceptance criteria

- [ ] `annotationsByLine` returns an array of length `lineCount` where index `stepLines[i] - 1` is `annotations.steps[i]` and every other index is `null`. A unit table pins: blank, comment, `start` and unparseable lines between steps map to `null`; a text with a trailing blank line has length `lineCount`; step lines `[2, 4]` of 5 lines give `[null, a0, null, a1, null]` (this fails an off-by-one that puts `a0` at index 2).
- [ ] After a run in the Text view, every step line's `build-order-line-annotation` shows `step-started` and `step-finished` text equal to the same step's `step-started` and `step-finished` in the table view for the same build, and its `data-kind` equals that table row's `data-kind` (acceptance, reading both views for one build).
- [ ] The `li`s for blank, comment and `start` lines contain no `step-started` and no `data-kind`. A step line whose `annotation.run` is null (not aligned to the shown run) has `data-kind`, no `step-started`, no `step-finished`, no `data-status` and no warning background, as `StepRunCell` does for that case.
- [ ] A step whose run is `not-reached` or `waiting` reads an en dash for both times (the text `formatStepTime` and `finishedText` return, shown through `StepTimes`), has `data-flagged="true"`, and its computed background differs from an unflagged step's, as in the table. The `li` uses `annotationToneClass`, not a copy of its rules. (respec 1)
- [ ] The annotation `li`s align with the textarea's lines: for every line, the annotation `li`'s top equals the line-number `li`'s top and its height equals the line-number `li`'s height, read in one `page.evaluate`, with a build that has a `start` line, a blank line and a comment line between steps (an empty `li` that collapses fails it). After a run at 1280 px the Build panel has no sideways scroll (`scrollWidth <= clientWidth`), the textarea's right edge is inside `panel-build`, and SGS-108's Text-view layout check still passes. `workbench.module.css` gives the annotation column a fixed width and keeps `min-width: 0` on the textarea (a CSS rule, not a 390 px test). (respec 1)
- [ ] Before any result (`annotations === null`), `build-order-annotations` and `step-kind-legend` are absent (count 0). After a result, `step-kind-legend` is visible above the textarea and there is exactly one in the page; switching to Table view still leaves exactly one. A start-only text shows no legend (`lines.steps.length === 0`), and a text with a syntax error on one line and valid steps on others still shows it. (respec 1)
- [ ] Stale dims them: with `page.route(SIMULATE_PATH)` holding the response after the first run, changing a step's text in the Text view gives the aligned steps' `li` `data-stale="true"` and computed opacity `0.5`, and the changed step's `li` has no `step-started`; releasing the route returns opacity to `1` and removes `data-stale`. Each test first asserts the API status it relies on.
- [ ] With a syntax error on one line, the other step lines keep their annotations (dimmed); the erroring line's `li` is empty.
- [ ] Pointer enter on an annotated step's `li` shows exactly one `chart-step-band` in each of the four charts with `data-from` and `data-to` equal to the API step's `startedAt` and `completedAt` (the same span the table row gives for that step) and sets `data-gutter-active="true"` on that `li` and on no other element, and no element in the page has `data-active="true"` from the gutter; pointer leave removes the bands and the attribute. Enter on a not-reached step's `li` draws no band (count 0 in each chart) and the `li` reads `data-gutter-active="true"`. A break it must catch: the gutter setting `data-active`. (respec 1)
- [ ] Caret: the test starts with the textarea focused (`select` also fires on a focusing click, so focus first); clicking a step line, then `press('ArrowDown')` (`keyup`) onto another step line, shades that step each time (one `chart-step-band` per chart with that step's `data-from`/`data-to`); moving it to a blank or comment line clears the shading; blurring the textarea clears it. (respec 1)
- [ ] Last event wins: with the caret on step line X, entering gutter line Y shades Y's step, and leaving Y clears the shading (no band for X), until the next caret event shades the caret's line again. The test must fail on an implementation that restores the caret's step on leave.
- [ ] The text view paragraph in `docs/aoe4-build-order.md` describes the gutter annotations, the hover and caret shading and the last-event-wins rule, states that the legend is above the Text editor as well as above the step table, and no sentence says the gutter holds only line numbers or that the legend is only above the table. (respec 1)
- [ ] The gutter `li` renders its times through `StepTimes` imported from `step-annotation.tsx` (no local `step-started` or `step-finished` markup in `build-text-editor.tsx`), `npm run lint:dup` reports no duplication between the gutter `li` and `step-annotation.tsx`, and `git grep -n "data-active" -- components/apps/aoe4-build-order/build-text-editor.tsx` matches nothing. (respec 1)
- [ ] No INVARIANTS.md regressions
