## Context

The Units chart draws one line per unit tier (`Veteran Spearman (tier 3)` and so on), so one unit line splits into several colours and a veterancy upgrade is not visible on it (M11.2). This ticket draws one line per unit line, all tiers summed, named by the `lineName` SGS-191 adds, and puts a dot on the line where each upgrade of that line finished (SGS-191's `ChartMarker.unit`). A pinned run gets the same dots as dashed-outline rings on its dashed lines.

## Scope

All paths under `components/apps/aoe4-build-order/` unless noted. Read at the end state of the Depends-on tickets (SGS-191 for the result fields; SGS-197, with SGS-195, SGS-196 and SGS-194 under it, for `line-chart.tsx`, `results.tsx` and `chart-zoom.ts`): `UnitSeries.lineName` and `ChartMarker.unit?` exist; `chart-zoom.ts` exports `TimeWindow`; `SeriesChart` is a `tbody`, takes `markerView`, holds the time window of `useChartZoom` (`shown`) and draws only what lies in it. Use the design's names exactly.

- `result-series.ts` (C16): add `unitLineSeries(run): ChartSeries[]`, one series per `baseId` in order of first appearance in `run.unitsProduced`, `key` = `baseId`, `name` = that entry's `lineName`, `values[i]` = the sum of `counts[i]` over every entry of the `baseId`. `unitsProducedSeries('units', run)` returns it. Add `interface UpgradeDot { key: string; label: string; at: number }` and `unitUpgradeDots(run): UpgradeDot[]`: one dot per `run.markers` entry that has `unit` whose value is a key of `unitLineSeries(run)`, in marker order, `key` = `unit`, `label` = the marker's label, `at` = the marker's `at`. Delete `unitSeries`; `results.tsx` (it uses `ReturnType<typeof unitSeries>` as a type) and the tests that import it follow.
- `result-series.ts`, new pure function `visibleUpgradeDots(dots, run, shown, hidden)` (not in the design; added to CONTEXT.md Key surfaces on merge). `run` is one run's drawn lines as `{ times, series }` (the shape of `PinnedSeries`), `shown` is a `TimeWindow`, `hidden` is the series legend's hidden-key set. It returns the dots the chart draws for that run, each an `UpgradeDot` plus its y value (the type's name is the implementer's choice). It owns every rule that decides whether a dot is drawn and where:
  - Per-run rule (B-U3): a dot is kept only when `run.series` has a series with its `key`. This is the only place the rule lives; `SeriesChart` does not filter dots itself. (`unitUpgradeDots` already drops markers with no line; this rule also covers a dot list passed with a stale key, and the pinned run is judged by its own series.)
  - Hidden line (B-U4): a dot whose `key` the legend hides is dropped. The pinned run is checked with the same base key, since one legend key hides both lines (`isLineHidden` in `chart-rows.ts`).
  - Window (B-U8, B-Z7): a dot is kept only when `shown.from <= at <= shown.to`.
  - Value (B-U2, B-U5): y = `valueAt(run.times, that series' values, at)`.
  - Kept dots stay in input order, and same-instant dots are all kept (two entries with equal `at` and y).
- `chart-rows.ts` (C16a): add `valueAt(times, values, at): number`, linear interpolation between the samples around `at` (the line recharts draws), `values[i]` when `at === times[i]`, the last value past the last sample.
- `line-chart.tsx` `SeriesChart` (C13, dot parts only): new optional props `upgradeDots?: readonly UpgradeDot[]` and `pinnedUpgradeDots?: readonly UpgradeDot[]` (both default none; `pinnedUpgradeDots` is ignored without `pinned`). It passes the current run as `{ times, series }` and `upgradeDots`, and, only with `pinned`, `pinned` and `pinnedUpgradeDots`, each with `shown` and `hidden`, through `visibleUpgradeDots`, and draws exactly what that returns. Draw order inside the plot after the lines: pinned dots, then current dots (B-U9).
  - Current dot (B-U2): `ReferenceDot[data-testid=chart-upgrade-dot]` with `data-series` (line key), `data-label`, `data-at`, a `<title>` child in `markerLabel` form (`chart-markers.ts`), at `(at, its value)`, radius 4, filled in the line's colour (`seriesColor` of the series' index in `series`) with a white stroke.
  - Pinned dot (B-U5): `ReferenceDot[data-testid=chart-pinned-upgrade-dot]` with `data-series` = `pinnedKey(key)` (the pinned path's own `data-series`), `data-label`, `data-at`, a `<title>` child of the form `<label> (pinned) <m:ss>` (the `chart-pinned-marker` title form), at `(at, its value)`, radius 5, white fill, a dashed stroke of width 2 in the pinned line's colour (`pinnedColor`). The dash pattern and the stroke details beyond that are the implementer's choice (design: open styling).
  - The dot's `ifOverflow` is the implementer's choice: the explicit window filter in `visibleUpgradeDots` already keeps out-of-window dots out of the DOM, whatever recharts would discard on its own.
  - The marker control (`markerView`) does not affect dots (B-U7).
- `results.tsx`: in the Units view the Units chart passes `unitUpgradeDots(result)` as `upgradeDots` and, only when a run is pinned, `unitUpgradeDots(pinned)` as `pinnedUpgradeDots`; computed once per run. The Buildings view and every other chart pass neither (B-U6).
- Tests the change can break (search found these; the rule is general): every unit test of `unitSeries` and of the Units view series (examples: `result-series.test.ts` cases for `unitSeries`, which pin names like `Spearman (tier N)`, and `unitsProducedSeries('units', ...)` equal to it) is rewritten for `unitLineSeries`; every acceptance assertion that keys the Units chart's paths by per-tier `unitId` is rewritten to key by `baseId` (example: `acceptance/aoe4-build-order-pin-compare.spec.ts`, the loop over `first.unitsProduced` `unitId`, and the pinned-only-series case, which must be rechecked against the new keys). `acceptance/aoe4-chart-views.spec.ts` "Units produced starts as Units; ..." compares Units legend names with the Buildings names and keeps its assertions; its Buildings cases count `path[data-series]`, which dots are not. Any other test keeps its expected values.
- Docs: `docs/aoe4-build-order-ui.md`, the chart series table row "Units produced (Units view)", says each `unitsProduced` `unitId`, in result order, is a series named `<name> (tier <tier>)`. That becomes untrue; rewrite that row to the series this ticket draws (key, order and name per `unitLineSeries`, tiers summed). The dot description and the sentences around the table stay with SGS-200 (M11 docs).

**Out of scope:** the engine and API (`lineName` and `unit` come from SGS-191); the marker control, zoom and window math (their tickets); the Buildings view; Gather rates and resource charts; storing dots in `StoredPin` or any schema, OpenAPI or pin-storage change (a pinned run is re-simulated from its text and already carries `markers[].unit` and `lineName`); a vertical line per upgrade; docs beyond the one table row.

## Acceptance criteria

- [ ] `unitLineSeries` (B-U1): one series per `baseId` in order of first appearance in `unitsProduced`, `key` = `baseId`, `name` = `lineName`, `values` = the per-sample sum over the `baseId`'s entries. A unit test uses a result with one `baseId` in two tiers whose counts differ per sample and a second `baseId`, and fails if the series are keyed by `unitId`, ordered by tier or by key, or take one tier's counts instead of the sum. An empty `unitsProduced` gives no series. `unitsProducedSeries('units', run)` equals `unitLineSeries(run)`; `'buildings'` is unchanged.
- [ ] `unitUpgradeDots`: a unit test covers a marker with `unit` set to a produced line (a dot, `key` = `unit`, with the marker's `label` and `at`, in marker order), two upgrades of one line (two dots), a marker with `unit` whose line the run never produced (no dot), and markers without `unit` including age-ups (no dot). It includes a second run whose upgraded line the first run lacks: that run's dot is kept, keyed by its own line.
- [ ] `valueAt` rows: exactly on a sample, between two samples (the interpolated value, with a non-integer result), and past the last sample (the last value). A test fails if the function returns the previous sample's value between samples.
- [ ] `visibleUpgradeDots` (respec 1): a unit test in `result-series.test.ts` covers several dots on one line (all kept, in input order), two dots at the same instant (two entries with equal `at` and value), a dot whose key is not in the run's series (dropped), a pinned-only line (a run whose series hold a line the other run lacks keeps that line's dots), a dot of a hidden key (dropped), dots exactly on `shown.from` and `shown.to` (kept) and just outside either (dropped), and a dot between samples (value from `valueAt`). The test fails if the stale key, the hidden key or an out-of-window dot is kept, if a same-instant duplicate is dropped, or if the value is the previous sample's value.
- [ ] Units view lines (B-U1) (respec 1): on the `ENG Knight/Longbow (King's Palace)` template at its default duration, the acceptance spec first asserts from the API result that `longbowman` has entries in two or more tiers, then checks exactly one `path[data-series="longbowman"]` in the Units chart, no path keyed by a `unitId`, and that the legend item names equal the `lineName`s of `unitsProduced` de-duplicated per `baseId`, in order of first appearance; the y label stays `Count`.
- [ ] Current dots (B-U2) (respec 1): on that template the spec first asserts the API result has a marker with `unit: 'longbowman'` (for example `veteran-longbowmen`), then checks one `chart-upgrade-dot` per such marker, `data-at` equal to the marker's `at`, `data-series="longbowman"`, and that each dot's centre lies on that line's drawn path (centre and path read in one `evaluate` under `expect.poll`; it fails if a dot is drawn at the previous sample's value or at y 0). The dot is filled in the line's stroke colour with a white stroke (computed attributes), and the `<title>` in the dot's group reads in `markerLabel` form (the marker's label and its `m:ss` time).
- [ ] Pinned dots (B-U5) (respec 1): the spec pins that run (`pin-run`) then runs the same template at a shorter duration whose end is past the first `unit: 'longbowman'` marker (asserted from the API first, and before the last if there are two). It checks one `chart-pinned-upgrade-dot[data-series="pinned:longbowman"]` per pinned marker, each at its `data-at` and lying on `path[data-series="pinned:longbowman"]`, drawn with a white fill and a dashed stroke in that path's colour, with a `<title>` in its group of the form `<label> (pinned) <m:ss>`; `chart-upgrade-dot` appears only for the current run's markers before its end. Unpinning removes every pinned dot; re-running recomputes both kinds.
- [ ] Hidden line (B-U4): in the same spec, hiding `Longbowman` in the series legend removes both kinds of dot and hides its two lines; showing it brings them all back.
- [ ] Marker control (B-U7): hiding the `unit-tier` kind in the marker control removes the `unit-tier` vertical lines and leaves both kinds of dot drawn.
- [ ] Buildings view (B-U6): with the Buildings view selected, no `chart-upgrade-dot` or `chart-pinned-upgrade-dot` exists, and the other charts have none in either view.
- [ ] Window (B-U8): with the Units chart zoomed so that a dot's `at` falls outside `[from, to]` (asserted from `data-zoom-from` and `data-zoom-to` and the API markers first), that dot and, with a pin, its pinned dot are not in the DOM, and a dot inside the window is. A test fails if dots ignore the window.
- [ ] Overlap (B-U9) (respec 1): in the acceptance spec, with the same build pinned and shown again, a current and a pinned dot share each point: both are in the DOM, the pinned dot precedes the current dot in document order, and the pinned dot's radius exceeds the current dot's (read from the rendered circles).
- [ ] Docs (respec 1): the "Units produced (Units view)" row of the chart series table in `docs/aoe4-build-order-ui.md` names the series `unitLineSeries` draws (key `baseId`, name `lineName`, tiers summed), and no row of that table still names a per-tier `unitId` series.
- [ ] Existing tests: `acceptance/aoe4-build-order-pin-compare.spec.ts` keys the Units chart's paths by `baseId` and still asserts that each pinned line is dashed and the current line is not, and that a pinned-only series gets one dashed legend item that hides its dashed line (its assertions are unchanged apart from the key). Every other test keeps its assertions apart from the `unitSeries` tests rewritten for `unitLineSeries`.
- [ ] No INVARIANTS.md regressions
