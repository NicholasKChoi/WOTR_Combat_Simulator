## Patterns

### 1. A ticket that turns on a new default lists named tests instead of a rule for them (SGS-031: 4 bounces, 1 more in SGS-032)

Evidence:
- `reports/SGS-031-spec-gate-1.md` gap 1 and `reports/SGS-032-spec-gate-1.md` gap 1: each ticket registers
  a handler (`build`/`move`, `research`) that SGS-030's Seam test asserts is missing; both tickets said
  "SGS-030's tests unchanged".
- `reports/SGS-031-implementer-1.md`: needs_spec at 1d514ee. `autoHouses` defaults to true (design/M2.md
  SimInputs), which lifts the supply-10 stop that 8 SGS-030 tests assert (5 unit, 3 acceptance). Re-spec 3
  listed those 8 by name.
- Run log 08:13 (11-01): needs_spec again after rebasing onto SGS-032 (ce342db): 2 tests in
  `research.test.ts` fail for the same reason. Re-spec 4 replaced the list with a general rule ("a test
  failing only because auto-houses default on may be pinned the same way if listed in the report").
- Re-spec 5 (`reports/SGS-031-spec-gate-5.md`): the diff check written for the list forbade the one
  `expect(` substitution the pin required.

Root cause / escape point: spec gap. The default and its effect on SGS-030's supply-stop tests were known
when SGS-031 was drafted (design says default true; SGS-030's ticket pins the supply stop). Escape point:
ticket agent; spec-gate 2 passed it. The general rule that finally worked is what the ticket should have
said from the start, since sibling tickets (SGS-032) merge first and add tests no list can name.

Proposal (engine): `agents/ticket.md`, section "Write", add a bullet after "Every doc the change makes
untrue ...":

```
- When Scope changes a default, or registers behavior that existing tests assert is missing, state a
  rule for those tests instead of a list of names: the one kind of edit allowed (for example, pass the
  old value as an explicit input), that expected values stay unchanged, and that the implementer lists
  every edited test in its report. Tests a sibling ticket adds before this one merges fall under the
  same rule; any other edit is needs_spec.
```

and `agents/spec-gate.md`, append to item 6 (**Dependencies and size**):

```
   A criterion that existing tests stay unchanged survives every default the ticket changes and every
   handler it registers: grep the tests that run with that default or assert that behavior is missing,
   including those in Depends-on and same-wave tickets, and confirm the ticket's rule covers them.
```

### 5. Stacked PRs cost more than they save under immediate auto-merge (3 issue lines, 5 rebase runs)

Evidence: run log 20:51 (`gh pr merge` refuses stacked PRs; manager used `PUT pulls/<n>/merge-async`),
20:53 (rebase agent left the sgs-027 worktree detached on a stale local branch; manager reset it), 01:22
(rebase agent could not repair native stack #36; GitHub blocks base edits while a stack exists). #33 and
#36 are stack PRs that 404 and never merged. Rebase agent ran 5 times in 6 hours, 4 of them only because
a stack parent was squash-merged. After 01:22 the manager stopped stacking ("batched alone so 031 rebases
onto it", 08:01) and the 11-01 runs needed one rebase (SGS-033, after a human-stop).

Root cause / escape point: tooling gap. With admin squash auto-merge, a parent PR merges within minutes of
opening, so a stack only adds a rebase per child plus gh-stack's merge and retarget limits. Escape point:
none possible in a gate; it is a profile setting.

Proposal (repo): `REPO.md`, line `stacking: gh-stack` becomes:

```
stacking: none                    # PRs squash-merge minutes after opening; gh-stack children need a rebase per parent squash and gh pr merge refuses them
```

Trade-off: a child of a high-risk parent waits for the human merge (as SGS-034 did for #39 in this window
anyway).

Root cause / escape point: spec gap. S3 bounds inputs and iteration counts, not what a route returns, so
the designer (wave 4 settled the 413 and trips merge for this route) and SGS-033's ticket set no cap, and
each later gate could only note it. Escape point: designer. One occurrence, but the same finding was raised

```

      an explicit cap checked before the loop runs; a route's response size is bounded by its caps.
```
