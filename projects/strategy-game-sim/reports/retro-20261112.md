## Patterns

### 1. Grep criteria that collide with tests (repeat after #10 was closed)
Evidence: strategy-game-sim SGS-135 RS1 (grep for removed ids vs absence tests), SGS-138 RS2 (search
criterion forbade the ids in tests), SGS-141 RS1 (end-state grep). All three tickets were written
15:44-15:51, after fcb83d1, which closed code-factory#10 as "superseded; reopen if grep-criteria
bounces recur in a milestone ticketed after that commit".
Root cause / escape point: spec gap in the ticket writer's instructions; caught at spec-gate each time
(cost, not escape).
RCA: the ticket writer writes "no occurrence of X in the repo" as an end-state check. Unit and
acceptance tests that assert X is absent must name X, so the grep can never pass once those tests
exist. fcb83d1 told the writer to check criteria it can run but not to scope greps away from test and
spec dirs, so the rule existed in spirit and did not fire for this case. The spec-gate caught all
three, at the cost of one re-spec plus one gate each. A scoping rule in ticket.md would have stopped
all three at writing.
Confidence: high - three occurrences, a repeat after a fix, and the edit names the exact check.
Proposal (engine): Issue draft: retro-20261112-issue-1.md "Ticket grep criteria must exclude tests and
specs (reopen #10)".

### 2. Ticket claims about existing tests go unchecked
Evidence: strategy-game-sim SGS-131 RS1 ("existing tests keep their assertions" contradicted the
removal test), SGS-134 RS1 (new write effect broke an existing spec on load), SGS-132 RS3 (implementer
needs_spec after a full implementation: two existing acceptance specs depended on the run-bar height);
previous window SGS-124 (same shape, retro-20261111).
Root cause / escape point: spec-missing; escape point ticket. 131 and 134 were caught at spec-gate;
132 escaped to the implementer, costing a full opus re-spec, gate, re-implementation and its own batch
gate (about $5 real).
RCA: manage.md and ticket.md already require "Scope states a rule for existing tests", so the rule
exists and did not fire: nothing makes the writer find which tests touch what Scope changes, so the
writer asserts "existing tests keep their assertions" without looking. The spec-gate only sees the
ticket text, so it catches contradictions inside the ticket (131, 134) but not a dependency it was
never shown (132: run-bar height). A required grep of tests/ and acceptance/ for the testids, storage
keys, functions and layout properties Scope changes, with each hit named in Scope, would have listed
the two run-bar specs for 132 and the conflicting spec/test for 131 and 134 at writing.
Confidence: high - four occurrences over two windows; the edit names exactly what the writer runs.
Proposal (engine): Issue draft: retro-20261112-issue-2.md "Ticket writer must grep existing tests for
what Scope changes and name each in Scope".

### 3. Test criteria that cannot fail
Evidence: strategy-game-sim SGS-128 RS1 (probe could not fail), SGS-135 RS1 (ArrowUp focus check
cannot fail), SGS-139 RS2 (collapse case cannot fail), SGS-133 RS2 (stopping rule passes vacuously),
SGS-132 Rework 1 (review: the written test cannot fail).
Root cause / escape point: spec-wrong at ticket; four caught at spec-gate, one at review (impl).
RCA: ticket.md applies the "would this fail if the code were wrong" check only to criteria labeled as
mutation checks. Ordinary test criteria ("focus stays on X after ArrowUp" when focus is already on X)
are not put through it, so the writer produces them and the spec-gate pays a round for each. The
review-side rule from #14 fired correctly on 132, so the gap is only on the ticket side. Applying the
mutation question to every test criterion would have flagged each of the four ticket cases at writing.
Confidence: standard - five occurrences, but the edit relies on the writer applying a question, not a
tool.
Proposal (engine): Issue draft: retro-20261112-issue-3.md "Ticket writer: apply the can-it-fail check
to every test criterion".
