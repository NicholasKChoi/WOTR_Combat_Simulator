## Gaps

1. **Acceptance criteria (unit test of the drag state) - not buildable as written - an implementer would have to invent a test seam or add a dependency.** The criterion asks for a unit test that covers "no state before the threshold, state after, cleared on drop, Escape and cancel, and the drop index equal to the one `onDrop` receives". `useChartDrag` is a React hook over `useState`/`useRef`/`useEffect` that calls `setPointerCapture` and adds listeners on the handle and `document`. The repo's vitest config runs the node environment on `components/**/*.test.ts` only, has no jsdom, happy-dom or testing-library dependency, and the existing component tests only use `renderToStaticMarkup`. A hook-level test cannot run. Proposed fix: require the pure part to move into a plain module with no React or DOM (a new file, since `chart-drag.ts` is declared untouched, or add to it and drop "untouched"): a function from the other groups' rects (top and bottom, in order), the pointer's y and the drag's start y, returning the drop index and the indicator's slot-boundary y; unit-test it as a table (above the first chart, between two collapsed charts, below the last, equal to what `dropIndexAt` over the midpoints gives, the dragged chart excluded). Have `onUp` and the indicator both call it (this also meets "one computation"). Move "no state before the threshold, cleared on drop, Escape, cancel and lost capture" to the acceptance specs the ticket already has for indicator presence, including the "state left set after Escape" failure case.

2. **Unverified assumptions and "No tint during a drag" criterion - the stated Chromium hover behavior is false, so the hover half of the criterion cannot fail - an implementer would build and test against a behavior that does not happen.** The ticket assumes that during pointer capture `:hover` matches the capturing handle's ancestors (the dragged row). I ran Playwright Chromium (the repo's chromium-1248) with a handle that calls `setPointerCapture` on pointerdown, moved the pointer over the handle's own row and over other elements while captured (`hasPointerCapture` true), and read `matches(':hover')`: the handle, its `td`, `tr` and the other elements all read false. So no row is hovered during a drag, and "a test fails if the dragged row keeps the hover tint" has no failing case; the Scope sentence "pointer capture keeps `:hover` on the handle's ancestors" is wrong. The focus half holds: in the same probe a mouse-pressed button does not match `:focus-visible`, script focus after a mouse click elsewhere does not, and a key press (Escape) on a mouse-focused button makes it match, so the list "Tab, arrow-key reorder, Escape during a drag" is right. Proposed fix: replace the hover-capture assumption with the observed one (no element matches `:hover` while the handle holds capture; after release the hover follows the pointer), keep the CSS rule that the dragged group's header row takes no tint while `data-dragging` is set (it is still needed for focus), and state the test setup that can fail: focus the dragged handle by keyboard first (Tab), so it matches `:focus-visible`, then press the pointer on that handle and drag; during the drag no header row's background differs from resting. Drop "pointer over the dragged row's own cells" from the criterion as a hover case.
