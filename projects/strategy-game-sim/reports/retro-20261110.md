## Patterns

### P1. Tests that cannot fail keep shipping to review, and review sometimes dictates them

Evidence:
- Review bounced tests that cannot fail on SGS-084 r1 (the test never reads gatherRates), SGS-099 r1
  (`omittedIssues > 0`), SGS-100 r1 (dispose test), SGS-109 r1 finding 1 (start-row test), and SGS-081 r6.
- SGS-108 r1: review required a `styles.stale` class assertion. In Vitest, CSS modules are a proxy
  (vitest.config.mts has no `css` option), so `styles.stale` is the string `"stale"` whatever the
  component does. Review 2 found that the assertion review 1 dictated could not fail.
- Review filed cannot-fail specs as non-blocking notes: SGS-108-review-1 N3 and N4, and the SGS-101
  build-store note. They went to BACKLOG.md lines 30, 56-61: build-store.test.ts:145,
  aoe4-step-annotations.spec.ts wiring and same-build checks, and step-annotation.test.ts:33-39 (CSS proxy).
- SGS-110: the keyup-only removal was not caught.
- Engine b394cb0 (11-09) added "rule out tests that cannot fail", and review.md's Bar already makes them
  blocking. The cases above show the rule is applied to the diff's own tests but not to tests review
  writes into a direction, or to tests it files as notes.

Root cause / escape point: test gap. These should be caught at the implementer, with acceptance-test's
mutation check as the backstop. Review is the escape point for its own dictated fixes and for downgrading
to notes. The CSS-proxy trap is specific to this repo and not obvious, so a repo lesson is the cheapest
guard.

Proposal (repo): `$FACTORY_DIR/LESSONS.md`, append:

```
- In Vitest, CSS-module imports are proxies (vitest.config.mts sets no `css` option): `styles.x` is always "x", so asserting a className contains `styles.x` cannot fail on a style bug. Assert the class only to prove which branch rendered, and pin visual state in Playwright with getComputedStyle.
  Why: SGS-108 r1 dictated a `styles.stale` assertion that review 2 found could not fail; step-annotation.test.ts:33-39 is in BACKLOG for the same reason.
```

Proposal (engine): `agents/review.md`, Bar section, replace the second "Always blocking" bullet:

```diff
-- a test whose name claims a check its assertions do not make, or that cannot fail (common.md, Tests).
+- a test whose name claims a check its assertions do not make, or that cannot fail (common.md, Tests).
+  This includes tests the diff adds that you would otherwise file as a note: never downgrade one to a
+  non-blocking note. When your direction dictates a test or an assertion, name the production change
+  it fails on (`file:line`, what to break) and check that the assertion reads a value that change
+  moves.
```

### P2. A visible defect in the diff's own new UI was filed as a note and shipped

Evidence:
- SGS-108-review-1 N2 noted that badge text wraps mid-word in the 74px run cell. It was filed as
  non-blocking because the fix conflicted with the 532/534 px fit constraint.
- M7-validate-1 D1 found the same defect after integration ("Villag/er", "Buildi/ng", "Econ/omy" at
  1280px, `overflow-wrap:anywhere`).
- Earlier analog: SGS-088 r1, where the disabled active button lost its fill and only the attribute was
  asserted.

Root cause / escape point: convention miss. The escape point is review, which saw it and applied
"unsure means a non-blocking note" to a certain, visible defect. When a visual fix conflicts with a spec
constraint, that is a spec decision, not a note.

Proposal (engine): `agents/review.md`, Bar section, add after the "Always blocking, as `contract` and
`test` findings" list:

```
Always blocking as a `correctness` finding: a visible defect in UI the diff adds or changes - text
broken mid-word, clipped or overlapping content, a state that renders the same as another. If the fix
would break a spec constraint (a width, a fit), the verdict is NEEDS_SPEC naming both, not a note.
```

Root cause / escape point:

Proposal (engine): `agents/spec-gate.md` and `agents/ticket.md`, add to the setup:

```
Run `git fetch origin` first. Read code at `origin/<base>`, or at the Depends-on branch tip when the
ticket has one (`git show origin/<ref>:<path>`, or a detached worktree), never the main checkout's
working tree, which may be stale or hold owner edits.
```

Proposal (engine): `commands/manage.md`, rework rules (near line 364, next to the text-only exemption):

```
A rework caused only by rebasing onto a sibling (a merge conflict, or a test made stale by the
sibling's change, with no defect in this task's own diff) is headed `## Rework N (rebase)` and does not
bump `reworkCount`, like a text-only rework.
```

### P5. Sandbox friction fills the run logs

Evidence: about 12 issue lines across runs.
- `git worktree prune` and `remove` fail with "Device or resource busy": 5 lines over 2 runs, including
  run-20261110-1043. `mount` shows `.git/worktrees/*` bind-mounted read-only by the sandbox, so this is
  not a WSL problem.
- lock.sh found its mutex on a read-only fs, and reported "lock NOT HELD" because the holder is `$PPID`,
  which differs per Bash call.
- EROFS on the npm cache, so simplify could not run eslint.
- EROFS on ~/.cache, so acceptance:setup could not fetch Chromium.
- A `.git/config` lock blocks `push -u` (2 lines).
- Repeated permission prompts for git push and gh.

Root cause / escape point: tooling gap (none possible at a gate). Agents spend turns rediscovering these
issues and log them as new ones.

Proposal (repo): `$FACTORY_DIR/REPO.md`, Tooling gaps, append:

```
- Sandbox: `.git/worktrees/*` are read-only bind mounts, so `git worktree remove|prune` fails EBUSY for
  worktrees created in this session. Leave them; the next run start (unsandboxed `git worktree prune`)
  cleans up. Not an issue line. `git push -u` failing to write upstream to .git/config is harmless;
  push with an explicit `origin HEAD:refs/heads/<branch>`.
- npm and Playwright caches: use the allowlisted ~/.npm and ~/.cache/ms-playwright; if EROFS persists,
  set `npm_config_cache=$TMPDIR/npm` for lint only.
```

Proposal (engine): `agents/suite.md` and `commands/manage.md` cleanup step: `A worktree remove or prune that
fails with EBUSY or EROFS is deferred cleanup, not an issue; note the path and continue.`

Owner action (not a file edit): run `scripts/allow.sh --with-run` from the code-factory repo so git push
and gh stop prompting.
