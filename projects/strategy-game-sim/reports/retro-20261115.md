### 1. Implementer-written acceptance specs reach review unrun or un-mutated
Evidence: strategy-game-sim SGS-137 review-1 (selector matches two labels; implementer-1: "Acceptance NOT
run. The role rules reserve acceptance runs for the acceptance gate"), SGS-139 review-1 (vacuous overlap
check; implementer-1: "The Playwright spec has no mutation checks because it was not run"), SGS-157
review-1 finding 2 (implementer-2: "I did not run the scratch-checkout base check", since the regression
was an acceptance test), SGS-135 review-1 and SGS-147 review-1 (specs run once, but a claimed case
had no break that fails it). run-20261112-1339 lines 14:42, 14:44, 13:59; run-20261112-2038 20:51;
run-20261115-1308 13:29.
Root cause / escape point: test gap from conflicting rules; escape point implementer (caught at review
each time, so cost, not escape).
RCA: the tickets' criteria name Playwright cases (SGS-139 "Playwright hover labels, no age-up label, no
overlap"), so the implementer writes the spec. `agents/implementer.md` Unit tests says "Do not author
acceptance-harness tests; a separate gate owns those", and `references/common.md` Processes (repeated
at implementer.md:108) says only acceptance-test runs `commands.acceptance`. The ticket outranks the
first rule, the second still holds, and so the implementer's mutation check ("for each test you write,
break the production code") and the Bug regression-at-base run (implementer.md:71) both skip the spec
it just wrote. Acceptance-test, which would run it, comes after review. Review is the first gate to
execute or mutate the spec, so every defect becomes a full rework plus a review rerun. 135 and 147 ran
their specs anyway (against the rule) and caught most cases, which shows the fix works. The 135/147
residue is per-claim mutation, the #41 unit problem. Letting the implementer run and mutate exactly
the spec files it adds or edits would have failed 137 on first run (strict-mode error) and 139 and
157 on the mutation and base runs, before review. Side effect: implementer time grows by one scoped
Playwright run (one to three spec files, 1-4 min here); ports are already per-checkout.
Confidence: high - five tickets, and the edit names exactly what the implementer runs and records.
Proposal (engine): Issue draft: retro-20261115-issue-1.md "Implementer runs and mutation-checks the
acceptance specs a ticket makes it write".

### 2. `Invariants: none` written although an INVARIANTS.md Paths glob matches
Evidence: strategy-game-sim SGS-144 RS3 (the only finding in that round; spec-gate-2: "Invariants field
misses A1-A3"), SGS-151 RS1 (spec-gate-1 gap 2), SGS-157 RS1 (spec-gate-1 gap 4). SGS-144's ticket said
"none (... no `Paths:` entry guards these rules)" while INVARIANTS.md line 50 has
`Paths: ... components/apps/aoe4-build-order/**`.
Root cause / escape point: rule exists and did not fire; escape point ticket, caught at spec-gate.
RCA: ticket.md says entries go in `Invariants` when "their `Paths:` match the files it touches, or they
guard behavior it changes". Writers read "adjacent" as "affected" and wrote `none` for CSS- or test-only
changes. The spec-gate applies the rule literally and bounces. Two of the three tickets had other gaps
in the same round, but SGS-144 spent one full re-spec plus gate on this alone. The check is mechanical:
the ticket's Scope names repo paths in backticks, and INVARIANTS.md Paths are globs. `ticket-lint.py`,
which every writer already runs, could flag `Invariants: none` when a named path matches a glob. That
would have stopped all three at writing.
Confidence: high - three occurrences, and the edit is a lint check.
Proposal (engine): Issue draft: retro-20261115-issue-2.md "ticket-lint: flag `Invariants: none` when a
Scope path matches an INVARIANTS.md Paths glob".
