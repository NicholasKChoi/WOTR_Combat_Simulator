## Gaps

1. Acceptance criteria 1 (auto-run status spec) - the mutation "let the held request through immediately" cannot make `expect(answered).toEqual([])` the failing assertion. An immediate response flips status to `current`, so the earlier `running` or `Computing the simulation.` assertions fail or race first, which is the exact shadowing the criterion forbids. An implementer cannot satisfy the criterion as written and would guess a wait length and mutation. Fix: state the property: "a simulate response that arrives after `running` and its text were observed (for example a held request fulfilled by a route after a delay shorter than the added wait) fails the `answered` assertion". Also state the wait's source (for example a named constant such as AUTO_RUN_DEBOUNCE_MS from helpers, or a fixed value that exceeds the mutation delay) and consider additionally asserting the status is still `running` after the wait, so the check observes the held state instead of only an empty list. Drop the "release in holdNextSimulate" mutation or restrict it to a delayed release.

2. Scope item 3 / criteria 3-4 (tab-order spec) - ambiguity on what "not the failing one" means and on the removed setup check. (a) Dropping the count assertion in `lastChart` removes the only check that every chart section renders; the ticket should say whether a rendered-chart check stays (as a later, separate named assertion after the order assertions, or `expect.soft`) so a missing chart is still caught. (b) For criterion 4, the stop-presence assertion 'every chart section has a handle stop' sits before the handle-before-caret loop and is a hard `expect`, so the implementer must choose between reordering, `expect.soft`, or per-chart filtering. With `expect.soft` both assertions report, so "fails X, not Y" is not testable. Fix: require that, under a caret-before-handle mutation, the first thrown assertion message is the handle-before-caret one (check each chart that has both stops first; run presence as its own assertion after), and that a missing stop still fails the spec through the presence assertion. Same wording for the column-swap case: the first failure is an `expectInOrder` message.

3. Acceptance criteria 2 (memory env isolation) - route choice leaves the "counter part" and key-function route underspecified. If the implementer picks "assert on the key functions directly", the check duplicates saved-builds.test.ts (line ~127-128) and named-builds.test.ts (line ~185), which already pin exact key strings, and it would not catch a store that stops passing env to the key function (for example `savedBuildKey('', id)` inside the store). Only a shared backing store exercises the store's own call sites. Fix: require the shared-backing-store route for the memory factory (an optional parameter or a test seam through which two stores with different envs use one backing store, with the existing single-argument calls unchanged), so that dropping env at the store's call sites in `buildMethods` or `bumpCounter` fails; keep the key-function route out or as an addition. Also "Each mutation ... recorded in the report" should name the report (implementer's) and the three mutation sites: `savedBuildKey`, `namedBuildKey`, `rateCounterKey`, each applied at the function and at the store call site.
